## 计分规则与不确定性

开发包给出的模型可以作为可配置的候选公式：

- 普通模式：`Accuracy = (P + 0.65 × G) / N`，`Score = 900000 × Accuracy + 100000 × C / N`。
- 普通 FC：`Score = 1000000 - 315000 × G / N`。
- 课题模式：`Score = 1000000 × (P + 0.65 × G) / N`，不加入连击分。
- 课题简化损失：`L = 7G + 20(B+M)`，只代表数量模型。

以下内容必须通过目标游戏版本的真实结算截图或人工校准样本确认后，才能标记为 exact：

1. 原始有理数到显示分数的取整/截断顺序；
2. 课题模式各音符类型允许的 Good/Bad/Miss 判定；
3. 铭牌阈值和边界是否随游戏版本变化；
4. 课题选曲规则，尤其是同一歌曲不同难度能否重复；
5. 普通模式中错误位置与 Max Combo 的完整谱面可达性。

实现必须使用整数分子/分母或等价的有理数表示，并把 `formulaVersion`、`chartVersion`、`confidenceLevel` 写入结果。浮点近似结果只能标记为 `approximate`。

## 算法边界

1. 只要已知 `N`、判定计数和 `C`，普通模式公式计算不需要谱面 JSON。
2. 只凭 P/G/B/M 总数不能恢复实际 Max Combo；需要谱面事件顺序或等价的断连模型才能做“谱面顺序验证”。
3. 课题模式不能沿用普通模式的 100000 连击分，也不能把所有 note 都视为可出 Good/Bad。
4. 输出分为“公式可达”“音符类型约束可达”“谱面顺序验证”三种可信等级，UI 不得把第一种说成实际必然可打。
5. 三曲搜索必须先筛选候选，再用排序、双指针、哈希或 meet-in-the-middle 搜索，只返回策略 Top-K/Pareto 集合，不保存全部三重组合。

## 纯静态部署可行性

产品核心适合纯静态部署：HTML/CSS/JS/JSON 托管在 CDN，公式计算在主线程，组合搜索和可达分数枚举在 Web Worker。玩家通过 sessionToken 直接读取 PhiHub 的 TapTap 云档，映射后的成绩只放在当前页面内存，不写入 IndexedDB。

云档读取依赖 `https://phib19.top:8080/get/cloud/saves` 的跨域许可。PhiTarget 不保存 token、成绩、导出文件或备份，也不提供 JSON/CSV 上传和手动成绩库。

## UI 方案与参考图映射

- 历史时间线图：借鉴“按更新时间分组 + 密集曲目卡”的信息结构，改为可筛选的响应式列表。
- B30/资料图：借鉴“玩家摘要 + 成绩卡 + 统计区块”，但首页聚焦目标分数和课题规划，不做 B30 查分站。
- 游戏结算图：借鉴分数、评级、Max Combo、ACC、P/G/B/M 的层级；曲绘仅在授权后接入，否则使用中性占位。
- 推分建议图：借鉴按 ACC 区间分组与候选卡片；PhiTarget 额外展示目标差值、可信等级和依据。

设计 tokens 需要集中管理背景、难度色、判定色、铭牌色、风险色。移动端 360px 宽必须无横向滚动，长曲名需通过宽度预算和字号适配保持可读。

## 风险与待确认问题

- 没有正式曲库和校准集，无法在当前提交中承诺真实歌曲结果。
- `phi-plugin` 是 GPL-3.0；即使公开可见，也不能直接移植其代码到尚未决定许可证的 PhiTarget。
- 参考图含曲绘、品牌标识和玩家数据，只能作为视觉研究资料。
- 课题判定资格、铭牌阈值和同曲重复规则需要按目标游戏版本核对。
- 数据导入格式可能缺少 P/G/B/M、Max Combo 或历史时间；适配器必须允许字段缺失并提示“数据不足”。
- 需要决定 PhiTarget 自身的开源许可证，并在提交真实曲库前确认数据再分发范围。
