# PhiTarget 生态功能分析与路线

## 定位

PhiTarget 适合把“目标分数、课题总分和可达性”做深，再补上玩家成绩分析和图片导出。它不需要复制一个完整查分站：PhiPlugin、phib19.top 和 Kyou 已经覆盖了通用查分、排行榜、社区内容和账号绑定，PhiTarget 的差异应放在可解释的计算、组合搜索和谱面结构约束。

## 外部功能盘点

公开的 [Catrong/phi-plugin](https://github.com/Catrong/phi-plugin) 已包含 B30/RKS、单曲成绩、推分建议、定数表、章节成绩、区间查询、历史 B30、排行榜、曲目搜索、曲绘、随机课题、曲目别名、谱面标签和评论等功能；README 也列出了主题、绑定和成绩更新入口。它使用 GPL-3.0，PhiTarget 可以学习功能边界和信息层级，不能直接复制其代码、模板或图片资源。

[phib19.top 的社区 API 说明](https://github.com/DeepSeek-V4-Pro/phigros-b30-plugin/blob/main/README.md) 显示，公开接口覆盖云存档读取、排行榜、RKS 排名、谱面平均 ACC、谱面标签、社区评论、公告和服务状态。曲目相关接口对 song ID 后缀和难度参数有特定约定，接口版本和 CORS 行为都可能变化。

[Kyou 的 Phigros 页面](https://kyou.net.cn/phigros) 更接近交互式网页：有 TapTap 扫码绑定、成绩缓存、RKS/B30 展示、单曲和谱面浏览、推分区、标签及评论等页面。它的账号和缓存模型适合参考交互流程；PhiTarget 默认只在当前页面内存使用 sessionToken，用户主动选择本机保存时才写入浏览器 localStorage。

[phigros.tools](https://phigros.tools/) 还展示了 QR 登录、sessionToken、TapTap 云档、Android USB 和本地存档导入等入口。这些功能能提升便利性，但 USB、本地加密存档和 OAuth 都会显著扩大浏览器权限与维护范围。

## PhiTarget 适合优先增加的功能

| 优先级 | 功能 | 用户价值 | 主要依赖与风险 |
| --- | --- | --- | --- |
| P0 | B30 / Best N 图片 | 输入 sessionToken 后在浏览器直接生成成绩图、下载或分享，满足最常见的查分需求 | 已实现基础版本；仍需要完整解析 score/ACC/FC、稳定的定数版本、曲绘 CORS 和自有 Canvas 渲染校准；不复制 PhiPlugin 模板 |
| P0 | RKS 与个人资料卡 | 展示 RKS、课题等级、Clear/FC/Phi 统计、已匹配谱面数和数据更新时间 | 当前云档解析已经有大部分字段；需要统一版本和缺失字段提示 |
| P0 | 单曲成绩 + 推分建议 | 对当前成绩计算单曲 RKS、达到下一个 0.01 RKS 所需 ACC，并按玩家已有成绩排序 | 需要准确的 RKS 公式和当前定数表；没有 ACC 时不能从普通模式总分反推出唯一 ACC |
| P0 | 课题总分三曲组合 | 已改为输入总分，搜索至少达到/最接近/精确命中的三首不同歌曲组合；可按个人成绩或公式模型 | 个人成绩模式只能说明云档已有成绩；公式模式必须标记为参考，不表示真实可打 |
| P1 | 高级曲库检索 | 按曲名、别名、曲师、画师、谱师、章节、BPM、物量、定数、难度、评级筛选 | 需要稳定的别名和元数据来源；搜索结果要继续使用虚拟列表或延迟加载 |
| P1 | B30 组成与 Best N 分析 | 查看每个成绩的单曲 RKS、排名、进入 B27 的门槛、Overflow 和推分空间 | 需要明确 P3+B27 口径、排序规则和版本标记 |
| P1 | 历史进步报告 | 比较用户主动提供的两次云档快照，显示 RKS、B30 门槛和进榜/掉榜变化 | 当前不保存成绩；可先支持一次性导出/粘贴的脱敏快照，或明确的本机可选存储 |
| P1 | 谱面结构与练习标签 | 显示 Tap/Hold/Drag/Flick 物量、同触点候选、长条时长和社区标签，帮助玩家选择练习曲 | 完整 JSON 体积和标签许可；标签只能作为社区信息，不能伪装成官方难度结论 |
| P2 | 社区只读信息 | 平均 ACC、谱面标签、评论、更新公告 | 依赖 phib19.top API 的稳定性、CORS、速率限制和接口许可 |
| P2 | 排行榜与全球排名 | 查看 RKS 排名、区间排名和榜单 | 需要实时 API，数据新鲜度和隐私提示；不应成为核心计算依赖 |
| P2 | 扫码绑定 / OAuth | 不再手动复制 sessionToken，降低使用门槛 | 需要官方 OAuth 或受控回调服务，不能自行模拟登录，也不能把 token 放入 URL 或日志 |
| P2 | USB 与本地存档导入 | 无网络时分析本地数据，接近 phigros.tools 的体验 | WebUSB、加密存档解密、浏览器兼容和法律/维护成本都较高 |

## B30 图片是否可做

可以做，而且适合纯静态网页。当前版本已经能从浏览器向 PhiHub 读取云档，玩家数据页与 B30 页共享当前账号，也支持用户主动保存多个本机账号；曲库有定数、曲绘和难度信息。实现路径是：

```text
sessionToken
  → 云档读取
  → 解析每张谱面的 score / ACC / FC
  → 计算单曲 RKS
  → 选出 Phi 3 + B27，并保留 Overflow
  → Canvas 绘制玩家资料、曲绘、成绩、ACC、评级和推分建议
  → 预览、下载 PNG、系统分享
```

首版不需要自己的后端，token 和成绩可以继续只存在 React state。曲绘只在生成时按需加载，失败时用文字占位；30～40 张图片足以控制内存和首屏压力。Canvas 生成后可以调用 `toBlob()` 下载，移动端支持时再调用 Web Share API。

要做到“和 PhiPlugin 结果一致”，仍有几项必须先校准：云档字段是否始终包含 ACC、FC 和新曲记录；目标游戏版本的单曲 RKS 公式与 B30 口径；定数表版本；曲绘 CDN 的 CORS；字体和图像资源的授权；以及 PhiPlugin 的排名、Overflow、推分建议排序。第一版应把计算版本、数据更新时间和 `approximate`/`calibrated` 标记画到图片上，遇到缺少 ACC 的记录时明确排除或标记，而不是猜测。

## 建议的产品顺序

1. 当前的课题总分三曲组合和 B30 图片先稳定下来，个人模式和公式模式分开显示。
2. 补充单曲成绩卡、B30 明细表和推分建议，复用现有曲库与云档解析。
3. 增加高级检索、定数表、谱面结构和社区只读标签。
4. 最后评估历史快照、排行榜、OAuth 和 USB 导入。它们都需要额外的隐私、接口稳定性或浏览器权限设计。

## 设计边界

- 不把 sessionToken 写入 URL、IndexedDB、日志或 PhiTarget 服务器；仅在用户主动保存账号时写入当前浏览器 localStorage，并提供账号移除入口。
- 不把云档成绩上传到自己的后端；需要历史比较时让用户主动导入脱敏快照，或明确开启本机存储。
- 不直接移植 GPL 插件代码，不打包第三方曲绘、字体和模板；图片生成器使用自己的 HTML/Canvas 布局。
- 社区标签、评论和平均 ACC 要显示来源、更新时间和“社区信息”标记。
- 所有结果区分公式可达、音符类型约束和真实谱面验证，不能把定数或 RKS 当作个人必然可达能力。
